# 公平比较与报告

先说清要回答的问题：比较用户各自自然的完整路线、相同语义下的实现，还是某个内部机制。
三者都可以测，但结论范围不同。不同缓存 dtype、额外功能或不同完成边界不能直接排名同工实现。

## 先对齐实际工作

检查双方源码与自然调用，记录会影响结果的差异：

| 方面 | 需要说明的内容 |
|---|---|
| 输入与结果 | 模型/权重版本、形状、分布、dtype、量化、scale、精度与正确性容差 |
| 执行方式 | backend、ISA、batch、线程、并发、布局、别名、buffer 与状态复用 |
| 准备 | 加载、解码、repack、上传、prepare/compile、allocation 与 warm-up |
| 完成 | 提交、结果可见、wait、错误、状态提交、输出释放和延迟回收 |
| 资源 | 实际分配/驻留/峰值、workspace、CPU辅助线程、内存搬运与能耗 |

“都调用一次 run”不代表做了同样的事。沿实际执行路径确认工作发生在计时前、计时内还是计时后。
GPU 计时需要明确测设备 kernel，还是主机提交到同步完成的整次调用；异步提交耗时不能当推理耗时。
需要 adapter 补齐语义时，把它的成本计入；无法对齐时分别报告自然路线的绝对成本。

例如：参考在计时前把 FP8 KV 展开为 BF16，而 HYLE 在计时内解码 FP8，这可以比较两种缓存方案，
却不能说明同输入实现谁更快。同工比较应从同一份驻留 FP8 数据出发；冷准备成本另外报告。

## 测量与数值

- 先检查输出正确性，再测 release 产物。参考若需修复同步或其他错误，保留原错误与修补内容，标明
  实际比较的是修复后版本；数值失败的用例不产生速度排名。
- 按真实任务选择冷启动、热调用或完整生命周期，分别报告，避免隐藏转换和清理成本。
- 用相同调用路径做 A/A，交换先后顺序；设备/runtime/allocator 的热状态不能由通用算术对照替代。
- 使用相关的 timer-floor、已知增量、代码/数据放置检查；操作过短时换成保真的聚合任务，避免测到仪器。
- 保留每个样本及失败，不剔除不利尾部，不从多个规模、顺序和分配位置中挑最好结果。
  配对、分层与区间方法见[测量与统计](instrument-v1.md)。

## 解释结果

同时给出绝对值、相对差和不确定性。稳定小幅落后应保留并调查；区间跨越无差异点，或换顺序/位置
后方向反转时，说明当前不能裁决。实用容忍区间与速度方向是两个问题：满足某个非劣容忍值不等于持平。

不要用吞吐收益掩盖尾延迟、内存、错误率或公平性损失。所需 workspace 和 allocator 实际占用分别报告，
预留相同大容量的实验不能据此宣称实际内存减半。功耗/能耗比较注明采集设备、采样区间与整机或设备范围。

对已排除测量问题的输项，按复杂度、搬运、分配、同步、争用、生成代码和真实消费者影响定位。
用户接口问题也要保留：多余转换、重复准备、隐藏同步和不自然状态管理都是实际集成成本。

## 保存足够复现的事实

报告链接实现/参考 revision 与补丁、构建命令和关键 flags、运行命令、输入、硬件/工具链、计时边界、
原始输出与分析脚本，必要时保存 artifact hash、trace、counter 或反汇编。说明失败、未验证项和结论范围。
已有结果保持原样；新发现用更正说明关联，不把修改后的合同写回旧数据。没有登记、模板或证书要求。
