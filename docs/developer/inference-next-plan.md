### 合并 decode 的统一算法

每进程先用实际 decode 输出数除以八轮不重叠 decode 墙时之和，再取各臂三个独立进程的中位数。当前八轮各输出 64 个，首 token 归 prefill，因此分子为 504 个 decode token。对外速度比为两臂中位数之比。

不平均逐轮 tok/s 或逐轮速度比；不相加重叠的 step 时间；ready 单列，ready 后首次录图／预热仍留在请求计时。完整进程墙时另列，不能把 decode 领先比例写成整进程领先比例。

| 记录 | Hyle／上游 MTP tok/s | 对上游领先 | 比较含义 |
|---|---:|---:|---|
| 首次 32K 子集窗口，`1622ad33d` | 140.129／108.901 | 28.7% | `.scratch/inference-mtp-small-vocabulary-20261104/window1/`；范围分别为 134.252–140.636、97.855–110.476 |
| 后续接力窗口中的同一旧实现 | 134.370／110.927 | 21.1% | `.scratch/inference-mtp-draft-handoff-20261104/window4/` 的 BASEK1；旧实现重跑也在约 134 tok/s |
| 本次续接复测，`8bc1d85ee` | 130.955／108.042 | 21.21% | `.scratch/inference-bf16-retest-20261104/window1/`；范围分别为 115.955–131.691、105.196–108.609 |

这些记录沿用同一合并公式，变化不能仅用“统计口径变了”解释。早期窗口波动较大，旧实现在后续窗口也没有复现 140 tok/s，不能把跨窗口差值直接归为代码退化。GPU 时钟或后台活动各自贡献尚未定量，不能写成已查明原因。最近的索引草稿头改动与同窗 HEAD 比较，两窗 MTP 为 −0.61%／+0.01%，收益是省显存，未证明可重复提速。

本次同窗早期版普通／MTP 为 97.04／129.14 tok/s；当前相对它为 99.90%／101.40%，范围重叠，没有观察到当前版整体退化。两种模式各 512 个输出与旧版逐项一致，三次重复一致，工作量、RNG 和真实退休检查通过。此项没有重跑 teacher，也没有测试尚未实现的完整多草稿接力。

用户提到的“合计快 24%”尚未定位到具体窗口；Git 中另有 `e23027045` 的 MTP **第 1 轮**领先 24.2%，该窗口八轮合并为 14.0%，不能混用。后续只引用明确附版本、工作量和同窗分母的数字，不为复现某个历史百分比单独重开优化。

### M1-11 量化数值资格和 ready 归因

**目标与范围：** 只测量和定位，允许扩展诊断消费者的导出，不改产品 kernel、量化数学或调度。只用本地 BF16、Q8_0、Q4_K_M，固定 tokenizer、GGUF 身份、BF16 KV、容量和同一组 teacher 前缀。

数值以 b12063 BF16 原模型为共同 oracle，同时列出 Hyle BF16 自身的对照误差。Hyle 和上游的两种量化均在相同强制前缀上导出完整 logits，报告 top1 一致率、平均 KL，以及每位置最大绝对 logit 差的 p50／p99。KL 固定为温度 1、完整词表上的 `D_KL(P_BF16 || P_quantized)`，离线稳定计算，不能用 top2 摘要代替。

**数值通过标准：** 每种格式 Hyle 的 top1 一致率不比上游低超过 1 个百分点，平均 KL 不高于上游的 110%；有限值、RNG、工作量和真实退休检查通过。达到这组有限负载资格后，才按用户修订替换量化下“同 GGUF 对上游分歧 <0.1”的门槛。未达标则沿同一前缀找第一个偏差明显放大的层；最多两轮无进展调查后报告，不放宽门槛或删除失败位置。BF16 仍沿用同精度 teacher 的近平局 <0.1 门槛。

ready 用 BF16 MTP 与两种量化 MTP 各 3 个新进程，把加载、权重／草稿头准备、Family 编译、捕获／预热和外部启动余量分开。先记录真实重叠，不能把并行阶段耗时直接相加。确认量化投影是否量化激活、实际 GEMV／GEMM 路径；当前量化跑的是完整草稿词表，不能先把多出的 1.1 s 归因于 32K gather。

**验收入口：** 新驱动在`.scratch/inference-quantized-qualification-20261104/`。已执行`python qualify.py build build2`、`python qualify.py prepare inputs1`、`python qualify.py teacher teacher1 --build-label build2 --input-label inputs1`，以及`python ready.py build ready-build1`、`python ready.py window ready-window1 --build-label ready-build1`，命令均以该目录为工作目录；新一轮使用新目录名。完整logits、共同BF16 oracle、KL及ready分段已输出，不能用旧top2脚本代签。`python tests/tooling/inference_upstream_compare_test.py`和`python tests/tooling/inference_nsys_compare_test.py`共24项通过。

**结束结果：** 给出每格式的资格结论和 ready 多出时间所在阶段。发现数值缺陷就先报告具体位置，本卡不顺带改 kernel；ready 改法交下一张卡。

### M1-8 量化启动和资源剩余项

**前提与范围：** M1-11 已完成归因；量化数值未合格时，相关性能只作为诊断。只处理已定位的重复加载、转换、冷准备或临时区持有，复用原 owner、预算和退休机制；BF16 已提交的瘦身不重做。

**实现顺序：** 先去除量化 MTP ready 的主要额外阶段；只有独立采样和持有关系能解释资源差距时，再处理对应常驻副本或临时区。若适合离线准备，保留源身份校验和正常默认使用路径，不让用户手选内部实现。

**拟定通过标准：** Q8_0／Q4_K_M MTP 外部 ready 均不慢于同窗上游 250 ms 以上；普通／MTP 合并 decode 不低于本卡起点 99%，每轮不低于 98%；BF16 普通／MTP 不退化，相关数值与状态检查通过。显存和私有提交不以新增大副本换启动时间，独立报告实际峰值。250 ms 是本计划的新目标，不是已经达到的结果。

**验收入口：** 基于 `.scratch/inference-quantized-review-20261104/window.py`、`validate.py` 和独立内存流程，加入本卡冻结起点作为同窗对照。默认构建，每臂 3 个新进程；BF16 使用[现有八轮驱动](../../.scratch/inference-indexed-draft-head-20261104/window.py)的同一流程作受影响回归。

**停止条件：** 最多两次实现尝试；两次都没有可重复的至少 50 ms ready 或 32 MiB 资源改善就停止。可以提交正确且不慢于起点的已验证部分，报告尚余差距，随后转接力卡。不开无边界的显存归零工程，不改 kernel。

### M1-10c 多草稿完整接力和自适应起草

**目标与范围：** 补齐草稿之间、验证／拒绝修复之后到下一批草稿的连续接力，复用 K1 的共同步骤驱动、原 Source、Queue、槽和 Completion。支持候选 `--mtp-max-drafts 3 --mtp-min-probability p` 的实际连续执行。沿用现有 32K 子集，不扩词表、不改 target head 或 kernel。

先完成配对归因，列出每验证轮的目标准备、草稿图调用、概率读回／判定、验证准备／绑定、GPU 活动外时间。已有 `.scratch/inference-mtp-adaptive-overlap-20261104/` 是前置诊断与原型，不是产品接力验收。

实现分两次尝试：先接通固定多草稿的原设备后继链，再把自适应停止信号接入同一链。若阈值读回打断后继，优先让设备控制真实草稿行数，或使用已完成的上一轮信号；未执行的草稿不能计为已提出，已执行但丢弃的工作仍须计账。第二次可以在第一次已验证结果上修正，不新增执行器或资源账簿。

候选必须同时证明 `decode_overlap=true`、确有后继提交和设备交接、以及 profile 中实际重叠；只改报告开关不算完成。显式检查 `draft_vocabulary_rows=32768`，补齐当前非零阈值与子集不兼容的接线，不能拿完整词表候选和 32K K1 混比。保留随机采样、modifier、设备和预算不适用时的正确回落。

阈值用独立于八轮验收的校准输入筛选，参考 p=0.95／0.98；报告每个门槛下第 1／2／3 个提案的数量、接受率和实际 K 分布。冻结阈值后再正式验收。32K softmax 的概率不等于完整词表概率，不能照搬完整词表 p=0.9 的接受率。

**正确性：** 同精度 b12063 teacher，argmax 分歧只允许上游 top1−top2 <0.1；模型完整状态、版本、pending、RNG、真实工作量、有序发布和最终退休守恒。覆盖拒绝／修复、EOS、额度和容量尾部、取消／背压、Source 拒绝及预算回落。不得因提前预测接受而提前发布状态。

**正式验收：** K1 冻结起点、新自适应候选和 b12063 同窗交错，每臂 3 个独立进程，8 个不同 prompt 各 64 输出；同窗附测固定 K2／K3，区分筛选和正式结果。合并 decode ≥ K1 的 105%，每轮 ≥97%，普通模式不退化，ready 增量 ≤100 ms。显存和私有提交另进程报告；只有全部达标才改默认。

**验收入口：** 扩展 `.scratch/inference-mtp-draft-handoff-20261104/window.py` 的 K1／K2／K3 三臂轮换和 `validate.py`，复用 `.scratch/inference-indexed-draft-head-20261104/` 的默认、长上下文与回落检查。新增阈值和后继链的驱动在本卡实现并记录实际命令，不直接运行旧脚本覆盖旧窗口。相关脚本测试为 `python tests/tooling/inference_upstream_compare_test.py` 和 `python tests/tooling/inference_nsys_compare_test.py`。

**停止条件：** 最多两次实现尝试。两次都不能使候选每验证轮墙时接近 K1 的 110% 以内，就附时间组成停止；接近但未达到正式速度／逐轮门槛，也不追加第三次。无论结果如何，本卡后结束 MTP 追速；未达标继续以 K1 为默认，已通过正确性且无退化的局部改动可单独提交。

### M2 和发布

按现有 M2-1 卡比较真正有人使用的场景：更大混合模型的 MTP、受限显存的 CPU＋GPU MoE、多轮与分叉会话。使用现有本地模型；缺权重时按仓库规则先取得下载授权。只选一个实测成立的主场景继续，目标为稳定 ≥1.3 倍，或提供上游没有的能力。

开始前固定端到端计时边界，包含所选请求的 prefill、decode 与必需恢复成本；冷启动和完整进程墙时另列。不能用局部 decode 的 21.2% 替代端到端收益。并发已有一次首批离线消费者对 HTTP server 的诊断，对齐条件不足以证明真实服务场景领先，不据此跳过 M2-1。

发布只使用已通过相应资格的配置，明确模型、硬件、精度、子集准备条件和上游版本。量化未合格时保留为诊断结果；MTP 第 4 轮落后和资源差距随结果公开。README 已有的结果入口继续维护，剩余重点是可运行的复现命令、原因清楚的文章和实际公开交付。

## 所有后续卡共同遵守的验收协议

- Windows 产品源码为准，默认 Release／`HYLE_COMPONENTS=engine`，复用现有构建和本地权重。冻结起点必须保留匹配的 EXE／DLL 集，不能混用旧 EXE 和新 SDK。
- 性能每臂至少 3 个独立新进程，同窗串行交错；保留约定的 GameViewer 后台并记录时钟。profile、计时、独立资源采样分开。上游服务使用端口 2048 和 `--metrics`。
- 每轮和合并 decode 同时报；首轮冷开销单列且仍计入完整数字。资源区分逻辑 payload、物理 GPU 采样峰、私有提交和 RSS，归池不等于物理释放。
- BF16 小词表与未准备文件的完整词表分别标明；改变草稿策略时记录接受／提案和目标计算次数。原始日志留在各卡 `.scratch/`，不新增证据 JSON、ZIP 或实验流水文档。
- 原卡的相关测试、数值、权限、失败与真实退休要求继续有效。两次没有可测量进展就停止；到停止点提交可验证部分并报告缺口，不自动追加方向。

常规测量入口为 `python scripts/inference-upstream-compare.py --help`，阶段包括 `standard`、`long`、`multi`、`memory`、`validate` 和 `analyze`。它的 `frozen` 臂使用旧参考程序的 CLI，不直接接受旧版 Hyle；旧／新版 Hyle 对比复用前述三臂驱动，不把不兼容的程序塞进 `--reference`。

验收结束按五项汇报：做了什么；验收命令和数字；失败或没做的部分；发现的问题；下一步。看板只按实际完成结果更新，不用旧计划、旧百分比或尚未运行的方案补完成量。
