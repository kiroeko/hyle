# R4 CUDA 长停顿：有界进度诊断

## Diagnostic-only audit

- baseline：`c2edb1c2`；[R4 当前卡](cuda-v1-four-route-foundation.md) 六个 owner 保持 BLOCKED。
- trigger：[两次资格停顿](../../../../evidence/correctness/cuda-r4-qualification-progress-stop/README.md)
  已超过 120 秒；第二次观察到大量 CPU 时间，但捕获启动晚于进程自行退出。24 次启动未再次定位，
  不足以排除或归因于任何具体产品/SDK/夹具组件。
- 本轮是独立只读诊断审计，不授权修改产品。原实现、默认规则、P1 门槛和停止裁决继续保留。
- 总预算：从本卡冻结起最多 30 分钟；最多一个不变诊断程序、最多 80 次启动或 8 分钟观察，
  二者先到即止。首个超过 10 秒的进程立即捕获并终止本批，不解释计时结果为产品性能。
- scope：同一完整 FFN 的真实已构建库；Windows 诊断程序增加共享内存阶段标记，记录 cold
  Context/packing/preparation、数值检查、warmup/measurement、teardown 所处位置。产品源码不变。
- observer：提前就绪、在另一个 P 核运行；child 整个进程仍为 CPU2 / AboveNormal。观察者先验证
  自己能在目标存活时读取阶段、线程角色/CPU 时间、RIP/栈候选和小型 dump，避免超时后才启动工具。
  独立 observer 不是给被测 CUDA 进程增加计算核。

## D1–D3 现场结论与定向恢复实验

2026-09-16 21:46 的第一进程 PID 36248 / 主线程 63172 在 10.031 秒阈值捕获，随后终止本批。
共享阶段为第一次 `cuda::create_context`；主线程 CPU 时间 10.094 秒，其余四线程各为 0。
离线使用 dump 的 x64 unwind 信息展开调用链，再与同一 executable 的 map/调用指令交叉核对：
`create_context_impl+0xba` 是 `cuDevicePrimaryCtxRetain` 返回地址，下面仍在 NVIDIA driver 的等待链。
本次现场尚未进入 `CompletionReaper::start`，不是其锁或 Sched 的现场证据。

原 D1–D3 观察批到此结束；已定位实际 API 和下游模块，尚未证明驱动内部缺陷或亲和性因果。
这项新事实允许一个独立、预先固定的恢复实验；不追加无目标复现，也不运行 P1：

- 保留同一个已构建 `phase.exe`、输入、优先级和 DLL。最多 12 次启动、总计最多 120 秒；
  本卡原 30 分钟总预算不延长。
- child 仍先在 CPU2 / mask `0x4` 运行；只有实际超过 10 秒且阶段仍为第一次 Context 创建，
  才对该存活进程操作一次。先捕获主线程/辅助线程现场。
- 将该进程允许集合扩为 CPU2+CPU4 / `0x14`，主线程继续强制 CPU2 / `0x4`；观察者迁到 CPU6。
  这只增加辅助线程的可调度 CPU，不修改 GPU/算法/数据，不给调用线程换核。
- 同一进程在之后最多 10 秒内完整退出才是这次 intervention 成功；保留全部数值输出与时间线。
  无复现或未恢复就停止，不能声称原因成立，不能据此重启 P1。
- 成功也只证明这台机器/软件/夹具下的进度约束；若要采用修正拓扑，须先冻结新采集合同和
  有限进度/A/A 回归，原失败数据继续排除，不外推所有驱动，不改产品锁或公共仪器。
