# 能力、组件与依赖

组件划分从用户任务、自然 API 和成本出发，再确定语义归属与依赖。
现有目录和 include 关系不能证明能力完整，也不能反过来否定合理需求。
[能力完整性](capability-completeness.md)说明需要检查的用户旅程。

## 何时拆成内部组件

拆分应有实际收益：隔离依赖或可选成本、避免依赖环，或让消费者只取得需要的部分。
组件应能独立说明所有权、寿命、失败、并发和复杂度。没有这些收益时，不为少一个文件或函数制造 target。

公开产品使用 `hyle::<product>`。内部 factor 用于源码和依赖组织，产品 façade 聚合它们；
不让普通用户理解内部拆分才能链接使用。SIMD 的不同实现和 ISA 仍属于一个 SIMD 产品。

## 一份依赖图

真实组件及公开、私有、构建期依赖由
[`HyleComponents.cmake`](../../cmake/HyleComponents.cmake)保存。
模块只列实现所需源文件和外部依赖，避免手工维护第二份内部链接图。

- 公开头或合同暴露的依赖属于公开边。
- 实现使用而不泄漏的依赖属于私有边。
- 构建工具和外部 Provider 不冒充 HYLE 的语义组件。

遇到环时先查语义归属和实现类型泄漏，再判断是否存在值得共享的小组件。
复用不能改变错误、所有权或常态成本；确实不能复用时说明技术原因。

## 公共接口

类型表达用户任务；默认值安全；拥有者与视图、同步与异步、有限与无限等合同明确。
正常用户不需要拼内部类型、模仿 benchmark 或了解第三方实现。
性能改进应保留这些合同；接口确有问题时按真实消费者证据调整。

验证组件选择、公开头、依赖和安装包是否一致；源码、安装后静态和共享消费都应能只选择产品根。
不再维护组件治理状态或收口流程。
