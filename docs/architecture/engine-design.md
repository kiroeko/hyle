# 通用推理引擎设计方向

本文记录通用引擎的职责、现有合同和本阶段冻结范围，不代表所有模型或平台已经实现。
token CLI与文本CLI／Responses的工作进程共用公共提供者装载和请求入口；Qwen有限日程与报告由独立诊断消费者处理。Graph、Compute和`engine/inference/`的原执行、资源与退休机制继续使用。

## 参考与选择

参考本地 llama.cpp `23b0202a1`：`tools/cli/cli-context.cpp` 的 CLI 可以连接已有服务，
也可以启动本地服务，再通过 HTTP 提交请求；`tools/server/server.cpp` 注册 `/v1/responses`，
`server-context.cpp` 将协议请求转换为内部任务，服务端管理请求队列、模型上下文与结果。
Hyle 借鉴统一请求语义和协议适配边界，不预先要求本地 CLI 必须经过 HTTP 或复制其调度器。

## 目标结构

```text
 CLI ───────────────┐
                    ├─ 输入适配 → 请求／输出合同 → 引擎运行时
 HTTP Responses ────┘                             │
                                      模型适配 + 后端能力 + 冷期计划
                                                 │
                                     现有 Graph／Compute／资源与退休
```

- **入口**：CLI 负责交互和本地参数；服务负责 HTTP、协议、连接和错误格式。两者使用相同的引擎请求语义；本地 CLI 可直接调用引擎，远端访问则经 HTTP。
- **文本和制品**：模型制品识别、读取、tokenizer、对话模板及增量解码归引擎装配层。tokenizer 必须匹配制品；模型数学不依赖 HTTP 或 JSON。离线生成的草稿子词表等可作为显式输入，运行时的自动生成与持久化另按真实实现验收。
- **引擎运行时**：接收请求，管理会话、停止策略、接纳、输出背压、取消和结果交付；复用现有请求循环与缓存机制。传输断开不等于设备工作已退休。
- **模型适配**：按制品选择模型实现，模型负责自己的权重语义、数学、完整状态和可用程序；公共合同不暴露 Qwen 的 GDN、Phase 或 MTP 特定布局。当前首先接入 Qwen3.5-2B，不声称其它模型可运行。
- **后端**：能力由具体后端和模型共同报告，冷准备选择路径；Graph／Compute 保持模型无关。编译期平台差异和冷期分派优先，不能在每个 kernel 上增加不必要的抽象或同步。

Qwen 的缓存和权重报告适配器放在其模型目录，公共报告层只处理通用观测。源码直接 include 的依赖方向由 `inference_architecture_boundaries_test.py` 检查；该检查不覆盖全部间接或链接依赖，冻结审查仍需检查构建目标。

这是职责方向，不要求立即引入公共 ABI、插件系统、动态加载框架、第二个执行器或资源账本。模型和平台是否能扩展，要以具体接口和调用链审查；未运行的组合只能标为理论设计。

### 扩展边界审查

以下是按现有接口作的理论审查，不代表这些组合已实现或运行：

| 场景 | 现有边界与需要补充的工作 |
| --- | --- |
| 不含 GDN 的 dense GQA 模型 | 新模型可实现 `ModelProvider`／`ModelExecutor`，自行装载权重、准备图并拥有自己的 KV 状态；公共请求和输出合同不要求 Qwen 的 GDN、卷积或 MTP 状态。需在 `model_catalog.h` 和构建装配中登记提供者，并实际实现和验证模型；当前没有第二个完整消费者。 |
| MLA、滑动窗口或不同草稿结构 | 当前 `GenerationBatch` 是文本 token 请求，并不规定注意力状态布局；模型适配器可选择自己的状态与执行计划。Qwen 的单 NextN 层检查属于其模型实现，不是公共约束。新的缓存淘汰语义、草稿制品或非文本输入仍须扩展相应合同，不能声称当前已支持。 |
| CPU／Apple Metal | `Backend` 在编译期组合对应端点，模型在冷期选择；实际操作、状态复制和退休仍须由对应后端支持。Qwen 的自动 MTP、有界 CUDA 快路及设备接力目前按 CUDA 选择，编码行复制能力也只对 CUDA 声明；这不是 CPU／Metal 的功能承诺。批量结果回读当前使用 CPU／CUDA 的共同 Compute Context 与可保留 staging 资源；资格不支持或冷期资源不足时回落到独立读取，原生错误不会被当作回落。其它后端若实现这条快路，需要接入对应资源与退休合同；普通推理能否完成仍取决于图中所有操作和资源合同，尚未在本目标中验证。 |
| 增加一种后端 | 现有端点是编译期枚举和静态组合；新后端需要修改 `Backend` 的类型、构造和资源绑定，不能仅注册一个插件。准备阶段选择路径，不要求在每个算子上动态分派；新增端点必须补齐实际能力查询、失败、完成观察和退休验证。 |

这一分工与本地 llama.cpp `23b0202a1` 将模型记忆与单次批次上下文分开、TensorRT-LLM `46d9966b54` 区分运行准备及资源释放的边界一致；具体接口不照搬。请求合同目前仅承载文本 token；内部请求可选择已准备的采样配置，工作进程可准备多套；公共文本服务仍只配置一套，跨 HTTP 请求保留会话尚未实现。冻结时应保留这些限制，不能用接口名称代替第二模型或其他平台的验证。

当前已有内部请求执行合同及入口。Qwen 适配器可以借用已创建的模型，也可以装载并持有模型；两条路径通过同一输出消费者交付 token，不持有第二份 KV 或执行器。工作进程可在模型运行时将等待请求接入已释放的槽位；槽位不足时继续排队。正式程序提供内部标准输入／输出 token 工作进程，文本 CLI 与 Responses 文本服务通过它提交请求，并以逐请求确认控制输出背压。实际支持的协议字段和限制见[文本接口指南](../user/text-api.md)。此前 BF16、Q8、Q4 的八轮 512 token 对照检查了工作进程、原入口及抽取前驱动；`d395885a01` 记录了旧入口与同窗上游的比较。旧入口只重编了入口和驱动对象，并复用当时底层库，不是独立旧版完整构建；这些历史结果不代表当前 HEAD 已通过最终性能验收。

内部 token 工作进程支持预先提交有限多轮，也支持打开输入后动态追加轮次并显式关闭；后续轮由原请求循环在上一轮发布后接纳，复用其会话与 KV。多轮接口按序交付 token 和从零开始的轮次完成事件，每个事件均须确认；单轮接口保持原有输出合同。后续轮按实际已提交的上下文检查容量；若放不下，仅该请求在真实退休后返回错误，提前停止释放的空间仍可用于下一轮。轮次完成不表示设备资源已经退休。新请求只有在原请求资源实际退休、输出终止事件被读取并释放后才能复用槽位；处于打开状态的其他会话不会独占全部空槽。内部 Qwen 执行器与工作进程可让多个已准备采样方案共存；公共文本服务仍只配置一套，HTTP 接口尚不提供跨请求持久会话。

常驻执行按预设容量准备 prefill，已知日程可以按实际长度准备；动态接纳也可能改变合批形状。不同计划的浮点输出可能不同，随机采样即使 RNG 游标相同也不保证逐 token 一致；量化贪心输出也可能随批形状变化。评估这类差异应使用相同前缀、上游同格式模型和 BF16 teacher，并单独检查 RNG、状态发布及资源退休，不能只比较不同的生成文本。

本机 CUDA、Qwen3.5-2B 的短提示数值检查中，此前普通路径与当前量化子集 K1 的各 8192 个同前缀位置均通过各自的既有相对 KL／top1 护栏；K1 的 8064 个位置使用实际验证器首行，teacher 基线沿用旧记录。覆盖八个背景重叠提示、256 个位置的 4K 检查也通过合计护栏，但单个 4K 提示的 32 个位置未通过该 top1 门槛；这些样本不代表所有输入。Q8／Q4 的 prefill logits 会随 GGML CUDA 融合或分块变化，关闭融合尚未证明能总体改善质量。层零探针会发布额外中间结果并可能改变融合：在一个 Q8 512-token 输入上，启用探针改变了融合路径的输出，因此探针的中间结果不能直接代指未插桩图。抽取前入口与当前入口在六个相关固定输入及融合设置中输出一致，但旧入口复用当前底层库，并非独立旧版构建。长前缀、其他批形状及具体融合差异仍有限制，不能把这些结果写成所有路径的数值等价或冻结完成。相关测试和数字保留在提交记录及本地日志，性能对照见[性能表](../developer/performance/decode.md)。

工作进程使用 `engine/inference/model_provider.h` 的公共装载配置和提供者合同，`engine/model_catalog.h` 在程序装配时静态组合提供者。每个提供者只读检查自己的输入格式，匹配后由其完整验证和装载；无匹配或多个匹配会报错。当前只接入 Qwen 提供者；token CLI 与 worker 由同一公共应用装配。该机制没有动态插件或第二个模型执行器，也不证明其他模型已支持。Qwen 装载器在冷期复用已有 MTP、设备验证和接力策略。公共 MTP 选择器只处理 off／auto／on、提供者声明的可用来源和拒绝原因，不推导后端、采样或缓存资格。Qwen 的默认准入、词表探测与多会话偏好位于 `engine/models/qwen35/mtp_default_policy.h`；既有默认选择和回落保持不变，显式 MTP 仍由模型能力和资源验证。显式 K1／K3 已用本机 Q4 和真实 tokenizer 验证两个并发 Responses 流，断开其中一个后另一个及后续请求完成；日志观察到两请求共同进入验证批次。单卡双请求、每臂三进程的短提示筛查中，现有子集头在中英混合组有收益，在另一组多语言提示上 Q8／Q4 K1 和 BF16 K3 均慢于普通生成；同组 Q8／Q4 全头 K1 则快于普通生成。该结果不能推出所有模型或设备的默认策略。另用旧日程的 8 个短提示自然生成，比较真实双请求验证器：相对上游 BF16 同前缀，K1 首行的 Hyle／上游单请求 Q4 top1 一致数为 129／146、127／146，平均 KL 为 0.07024／0.06996。K3 的 220 个位置包含 94 个首行和 126 个后续行，Hyle／上游 Q4 top1 均为 197／220，平均 KL 为 0.06650／0.06600；只统计实际提出 3 个草稿且验证 4 行的成员，后续行还要求先前草稿实际被接受、其预测与已发布 token 一致。诊断使用 commands 重放；这些经过筛选的小样本不代表多会话 MTP 的完整性能或数值质量已经验收。

文本层的 `engine/text/runtime.py` 负责消息编码、请求提交和有序文本交付；CLI 与 Responses 都使用这条路径。`contracts.py` 描述 token 传输合同，`worker_client.py` 连接内部工作进程；`server.py` 负责 HTTP 路由、连接和流式传输，`responses.py` 负责 Responses 字段与事件格式，`app.py` 在启动时组合入口和路由。输出消费者接收文本之后才归还 token 配额；传输失败由原请求的取消与退休路径处理。

## 请求与生命周期

模型装载和设备选择完成后形成可复用的运行上下文。每个请求拥有独立身份、输入、生成配置、停止条件和输出消费者；会话及模型状态的所有权应明确，不能通过协议对象直接修改设备事务。

当前内部装载合同将来源资产、执行准备和采样程序配置分开。采样参数的数值范围在选择模型提供者前检查，top-k 等依赖词表的限制由提供者检查。公共资产合同提供主来源和具名附加资产，由模型提供者解释角色和验证来源；Qwen 识别草稿词表与草稿头，未知角色报错。请求日程可携带初始随机种子；未指定时沿用模型默认值，接纳时生成游标，之后的随机位置属于会话已提交状态。工作进程的 `--seed` 是发给请求的默认值；Responses 尚不接收逐请求种子或采样参数。Qwen 内部装载合同可预设多套采样方案，请求按索引选择；内部 token 工作进程可逐请求传入方案索引、初始种子和草稿数上限，未准备的选择由模型拒绝。内部工作进程用可重复的 `--additional-sampling` 在冷期附加方案：值为 `greedy`、`random`，或 `random,温度,top-k,top-p`；索引 0 是默认方案，附加方案从 1 开始。请求选择已准备索引；草稿上限为零只禁用提案，不保证切换到普通生成状态。只有执行器声明可共存时，公共调度器才在同一执行期间接纳不同采样方案。各实际计算波仍按模型已有兼容条件分组。

引擎应能提交请求、交付有序增量输出、观察完成或失败、请求取消，并在消费者不能继续接收时施加背压。取消只停止后续可停止的工作；已提交设备工作的完成观察和真实资源退休仍走原 Graph／Compute 路径。模型请求槽位退休和下游输出槽位释放分别判断：正常消费须读到终止事件并释放；请求句柄被放弃时丢弃未读输出、请求取消，仍须等原模型确认退休才能复用槽位。文本增量解码需处理跨 token 的 UTF-8 边界；传输写入成功与模型状态提交是不同事件。随机数、状态版本、MTP 接受及输出顺序沿用现有正确性合同。

公共请求装配位于 `engine/inference/request_owner.h`：校验消费者的轮次通知能力，管理原 `TokenDelivery` 的稳定槽位，并依序服务输出、推进请求、观察退休和接纳输入。动态接纳先由模型作无副作用的校验，再准备模型私有载荷；公共层用原 `RequestLoop` 分配请求身份并绑定输出。只有校验阶段的参数或范围错误转为逐请求拒绝，准备或绑定开始后的错误继续传播，不伪造退休。输出槽位只能在原请求真实退休且消费者收到结束通知后复用。

Qwen 适配器仍负责完整模型状态、图准备、执行、输入载荷和真实资源退休。公共装配通过编译期绑定调用模型阶段，不创建第二个执行器、身份分配器或设备资源所有者。宿主执行器与 Qwen 使用同一接纳和输出装配；这只验证了该机制的复用，其他 Qwen 生成装配仍需审查，不能据此认定新模型接入已经完成。

能力和参数在装载、准备或请求接纳时校验并尽可能选路；不能提前确定的资源权限、Source 和完成状态仍在执行时检查。默认策略、正确性限制、性能选择分别表达，并能解释拒绝或回落原因；不以某次单模型测试结果伪装共同正确性条件。

当前有界请求的轮数、token 范围和输入／输出预算由公共接纳检查统一表达；Qwen 使用该检查，并在后续轮按实际已提交上下文检查新输入、上一轮 pending 和输出额度。这是已选择的有界政策，不强迫滑动窗口或其他模型采用相同容量规则。

### 混合请求的设计检验

以同一模型的三个并发请求为例：A 选择子词表草稿头和 K3，B 选择全词表头和 K1，C 使用普通随机采样。目标是共享同一份目标权重；每个请求独立拥有其输出配额、停止政策、会话状态和 RNG 游标。草稿资产与执行程序在冷期准备并保持不可变；请求引用它们，设备工作真正退休前不得替换映射或回收资源。草稿与验证方法由模型实现，不要求其他模型复制 Qwen 的 K 上限、状态布局或修复步骤。

调度应根据已准备程序的实际兼容性组成执行批；不能混合的请求分别运行，并避免不兼容请求永久阻塞其他请求。可混合的草稿深度、采样和词表由模型及后端能力决定，不预设所有字段必须相同。驻留会话数、单批序列数、在途深度及物理执行槽分别计量；准备多种方案时预算必须覆盖能同时存活的资产、状态和工作区。目标权重、激活、KV 与草稿头的编码和计算精度分别描述，不以一个“模型量化格式”代替。

共享前缀是可复制写入的不可变计算状态，必须包含续算所需的 KV、卷积和递归状态；完整会话检查点还包含 pending、草稿及 RNG。底层前缀目录按模型、数学身份和由可信调用方指定的共享域共同匹配；内部请求将该域传给 Qwen 的查找和发布。默认域 0 保留本地原有共享行为，并不自动隔离用户。服务若要启用前缀缓存，必须由可信服务层分配共享域，不能相信未经验证的客户端域值。Qwen 的 Q4 和 BF16 真实 prefill 状态已检查同域命中与跨域不命中，宿主测试覆盖 pin 与淘汰；公共工作进程尚未接线，不能据此声称服务具备租户隔离。本地 vLLM `276fbcff27` 在块哈希的额外键中包含适配器、多模态和可选 cache salt，可作为共享域设计参考。

现状仍不能执行上述三请求混合：Qwen 的缓存计划绑定普通或 MTP，装载时只选择一套草稿资产；公共工作进程未启用前缀缓存，HTTP 也不保留跨请求 KV。在同一推理模式下，Qwen 内部接口已用 BF16、Q8 和 Q4 短提示分别检查普通、K1、K3 的三套采样方案，包括初始混合批、动态接纳、独立 RNG 与拒绝非法配置。配置子词表时，未修改的贪心方案使用子词表，随机或带 logits 修改的方案使用完整草稿头；K1／K3 随机方案在三格式同前缀、同种子小样本中与未装载子词表的结果一致。BF16 另检查了已准备的 Q4 草稿头；默认随机或默认贪心均可与另一方案共存。显式子词表没有贪心消费者时仍会报错。

内部请求可以指定不超过已准备上限的每轮草稿数，同一 Qwen MTP 模型可接纳 K1 和 K3 请求，并按现有形状与采样兼容性组批；超出准备上限的请求在接纳时被拒绝。BF16、Q8、Q4 子词表小样本检查了混合 K、动态接纳和请求独立的 RNG。Q4 的八个提示产生 114 个真实双请求验证首行，K1 与 K3 各 57 个：两组分别与 BF16 teacher 在 51 个位置 top-1 一致，均与同格式 llama.cpp 的一致数相同，并通过既有相对 KL 护栏。这些短提示不能代表所有形状。零草稿上限只表示不提出草稿，仍使用 MTP 状态和程序，不等同普通生成。内部工作进程已提供请求级草稿上限，HTTP 尚未提供；贪心请求也不能在已装载子词表时独立选择完整头。

公共 `ModelExecutor` 最终仍调用 Qwen 的生成装配；第二个模型是否无需复制它，还没有实际消费者证明。多模型及多设备还需要独立的模型实例、预算与资源接纳合同，不能把单主端点加可选 CPU 辅助误写为多设备调度。

后端应在冷期提供真实算子、编码搬运、捕获、同步与退休能力，模型再结合自身数学约束选择程序；默认策略和测得的性能偏好与正确性限制分开。现有 CUDA 快路可以保留，其他后端当前只有理论审查。量化 tokenizer 子词表由固定提示及原 ID 顺序补齐，不能推断所有语言的接受率；加载后自动生成、来源绑定及持久化仍未实现。

## CLI 与 Responses

目标提供命令行入口和 HTTP 服务。协议边界需要能够容纳 OpenAI Responses、OpenAI Chat Completions 和 Anthropic Messages；先实现 Responses，其余两种在实现和验证前不声明支持。每个协议负责解析、字段校验、错误和流式事件转换，不把某一种协议的 JSON 对象作为模型或调度器接口。内部请求与事件须保留消息顺序、角色、内容、生成选项、使用量和完成原因，扩展内容类型时不能将其静默压成纯文本。

Responses 首版以文本请求和文本输出为目标，需明确并测试实际支持的字段、同步与流式行为、取消、错误以及使用量统计；尚不支持的字段或能力应明确拒绝。工具调用、多模态、服务端持久会话等按实际实现单独声明。流式协议的事件格式由适配层实现，参考 [OpenAI Responses 流式文档](https://developers.openai.com/api/docs/guides/streaming-responses)；模型线程只交付已提交输出，传输断连通过请求取消传播，实际设备退休仍由原执行链完成。

模板由模型制品及其配置选择，不能把 Qwen 的某个 Jinja 模板编码成通用消息合同。模板渲染、tokenizer 和增量文本解码属于文本适配层；缺失或无法执行的模板及不支持的消息内容应有明确结果。当前文本入口使用本地 Python tokenizer 和模板；`hyle::io::http` 提供 HTTP/1 帧处理，文本服务的监听、路由和连接生命周期由 Python 前端实现。服务默认端口为 2048，支持时默认启用指标；协议范围见[文本接口指南](../user/text-api.md)。

## 架构审查与冻结修复基线

2026-11-13，以`79c160bbf`为源码基线，最初静态审查沿应用、装载、请求、模型执行和文本交付的实际调用链检查职责与依赖，当时未构建或运行GPU。后续修复及实际验证见下文，全程未下载模型。
[两项核心期许](inference-principles.md)用于判断取舍：共同机制应降低新模型的接入成本；抽象应保留专用快路，将准备和选择留在冷期。它们不直接充当无限扩张的完成条件。

**结论：原有底层机制继续使用。当前需要关闭的是下列 R1–R4，而不是重写整个底座。**
`ModelExecutor` 进入模型私有生成函数、模型内部存在 Family／Phase 或 GDN 状态，都不是单独的缺陷证据。接入真正的新算子可能需要扩展 Graph／Compute，也不自动说明边界失败；需要检查改动是否属于新的计算能力，而非泄漏模型私有语义。

### 产品与诊断装配链

```text
token CLI：main → run_application（application.h）→ ModelProvider::load
           → GenerationDispatcher → ModelExecutor → 共同请求机制 → 模型步骤 → Graph／Compute

文本CLI／Responses：text/app → token worker → 同一application／提供者／请求链

显式Qwen诊断：diagnostic_main → qwen35::run → 有限负载／诊断配置
              → 同一模型冷准备与执行 → 完成观察 → 独立报告格式器
```

模型步骤进入Qwen是正常分工。正常产品入口不再默认转发旧驱动；新提供者不必实现Qwen的CLI或有限日程。

### R1：统一正常产品装载

基线问题是`run_legacy_cli`旁路提供者，并由Qwen驱动重新组装正常配置。现由[application.h](../../engine/application.h)统一解析CLI和worker配置，经同一`load_model`匹配、验证和装载；[model_catalog.h](../../engine/model_catalog.h)只登记提供者。
CLI请求与worker帧使用同一dispatcher。提供者自定义资产通过`ROLE=FILE`进入公共配置，角色语义仍由提供者解释。
旧重放、探针和JSON报告改为显式`hyle_qwen35_diagnostic`，不加入默认产品目标。

宿主使用非Qwen提供者检查了CLI／worker的等价有效配置、具名资产和方案选择，正常解析器不需为该提供者加分支。
本机Q4的普通贪心、K1贪心和普通随机各16个CLI／worker输出ID一致；未知来源、非法输入和worker上未使用的CLI请求参数明确拒绝。
这里没有声称新模型数学已经实现。

### R2：冷准备、请求执行和诊断消费分开

基线执行入口需要`NullBuffer`、报告流及旧有限负载参数。正常产品现在直接调用[generation_runtime.cc](../../engine/models/qwen35/generation_runtime.cc)的`execute_generation_sessions`，只接收公共批次、执行准备和输出消费者。

| 所有者 | 责任与依赖 |
| --- | --- |
| `ModelProvider`／模型装载器 | 来源、资产、端点、精度、状态容量和执行方案。每个所有者一个原Model。 |
| `prepare_generation_programs`／`prepare_generation_recordings` | 按配置和已到达输入准备程序、载体与录制；可复用准备保存原资源身份与失败状态。 |
| `generation_state.h`／`execute_generation_sessions` | 模型私有请求状态和推进适配，复用原RequestLoop、输出槽和步骤驱动。 |
| `Model`／Graph／Compute | 数学、完整状态发布、Source权限、实际完成和真实退休，保留原权威。 |
| `generation_diagnostics.h` | 借用本次已完成的只读观察；不得保留、重入执行或成为资源所有者。 |
| `generation_report.cc`／显式诊断入口 | 消费观察并格式化有限负载报告；正常产品不链接该格式器。 |

首次准备仍按需完成，准备失败后原所有者不能复用；下一批必须等原工作、输出与资源实际退休。
正常执行编译掉未使用的报告集合；身份、实际行数、权限及退休检查保留。诊断包装器使用同一执行实现，报告回调在原完成检查之后运行。
产品与诊断目标均已定向编译和链接；并发、采样、背压、取消、容量与拒绝隔离复核沿原执行链完成。
这些剩余模型代码已有模型／准备／诊断归属，不因仍存在Qwen私有函数而留下开放尾项。

### R3：Qwen选路归模型，通用层只保留通用合同

原公共`decode_route_policy.h`已经移至[模型目录](../../engine/models/qwen35/decode_route_policy.h)。公共层保留`RouteChoice`、原因枚举、工作负载事实及原资源合同；不规定存储草稿投影、单会话CUDA接力或三级流水。
正常装载器一次组装`ColdWorkloadFacts`及模型能力，供本次冷选择使用。明确的诊断消费者可以按其不同有限负载组装自己的事实。

| 门及事实 | 分类与归属；不满足时的行为 |
| --- | --- |
| 用户关闭overlap／MTP、草稿数为零 | 明确配置或路径不适用；不选对应可选路线。零草稿请求上限仍不等于另一个普通执行方案。 |
| bounded的自然请求、单会话、无prefix／planned、贪心及无CPU辅助 | 当前Qwen有界诊断准备的实现范围，不是通用引擎的数学定理。否则使用原有限日程／单步实现。scheduler不改变该工作负载上界，但可拒绝设备接力。 |
| MTP所需剩余位置、精确token ID表示、来源与资产身份、张量范围 | 真实容量或数值／来源正确性约束。按原规则裁剪、拒绝或走合法原路径；不以跑分代替。 |
| 设备链上限、K>1的存储投影、relay能力、commands／state trace、has_decode | 当前Qwen具体程序／交接的实现条件。按原因不选overlap，保留已有独立步骤。无decode只表示不需要该路线。 |
| 设备验证的MTP、K>1、链能力、单活动序列、relay、非commands、has_decode | 当前独立验证载体的能力。它仍可服务非存储投影或trace的独立草稿链，因此有意不照抄overlap的两项门；组合测试锁定这一不对称。 |
| resident默认单会话／单活动序列；auto MTP的CUDA、greedy及多会话偏好 | 模型的自动默认／已测偏好，不能当作引擎能力上限。显式选择仍受实际模型和后端能力验证。 |
| continuous依赖overlap／MTP、无prefix、单缓存会话、注意力及精确ID | 当前连续后继实现与表示能力；不满足时保留独立链或普通步骤。其他模型不继承该选择器。 |
| cache预算的验证关闭、深度3→2、overlap关闭 | `fits`提供真实资源约束；放弃可选路线的次序是Qwen冷政策。最小工作仍放不下则按原资源检查失败。 |

Qwen的选择、原因和降级顺序保持，现有组合检查覆盖验证／overlap独立性、无decode、resident偏好和逐级预算。
运行时的Source、状态版本、原队列权限与真实退休没有搬入冷策略，也不因计划选中而跳过。

### R4：准备方案的独立身份｜已关闭本阶段合同

- **基线问题：** 审查时的[ModelLoadConfig](../../engine/inference/model_provider.h)只有一份执行准备和按角色唯一的附加资产，额外方案仅为`additional_sampling`。请求可以选采样及草稿上限，但不能独立选择执行方案；零草稿上限不等同普通生成。
- **影响：** “子词表 K3／全词表 K1／普通随机”不能仅由当前请求合同准确表达。若继续把执行模式塞进采样索引或把零草稿伪装普通模式，会混淆状态、资源和兼容分组。
- **已有：** 来源资产、执行准备、采样政策已分层；请求 RNG、K 上限、多采样方案和兼容分批已有实现。
- **修复终点：** 冷期声明不可变执行方案，请求按独立身份选择；模型定义资产、完整状态、数学、兼容性与预算，采样程序和请求 RNG 各守原生命周期。同一目标权重可以被兼容方案引用，不能为公共抽象重复复制权重或建立新资源账本。
- **关闭条件：** 公共合同能表示上述三请求的选择、实际可共存性与不兼容分组；未准备或当前不支持的组合在接纳前明确拒绝，不能静默换模式。宿主覆盖混合选择、独立 RNG、拒绝隔离及在途方案不可替换；Qwen 复核现有普通／K1／K3 和多采样路径，零草稿的实际含义不变。

R4 要完成公共合同、选择与拒绝路径。它不要求本轮实现尚未交付的全部混合图组合；冻结记录只承诺实际已验证的组合。后续在模型内部增加一种方案，不应再改变请求身份、输出、取消或退休机制。

现有合同中，`ModelLoadConfig.execution` 只承载端点与容量，`execution_profiles` 声明具名的不可变执行准备；方案可覆盖来源的具名辅助资产，草稿深度和接力选择归方案。`ModelDescription.execution_profiles` 报告实际算法、草稿上限和对称的可驻留关系；这不授权将不同程序强行放入同一设备批。请求日程独立选择 `execution_profile`，采样索引、种子和草稿上限保持原含义。公共接纳隔离未知／不兼容方案，模型继续检查实际状态和资源。当前 Qwen 每个所有者仍只准备一个执行方案，明确拒绝额外准备；方案内部原有采样与 K 上限选择保留。

内部 token 管道的 P 帧在原 R 帧的采样索引前增加执行方案索引；`WorkerClient.submit`／`submit_turns`／`open_session` 的 `execution_profile` 参数使用它。默认请求沿用原帧和方案零。HTTP 尚不暴露逐请求执行方案。宿主已检查兼容 MTP 方案共存、普通方案不兼容时的拒绝与后续独立执行；本机 BF16／Q4 已检查方案零的原输出、非法方案拒绝及进程继续服务。

### 不列为本轮结构缺陷

- Qwen 的 GDN／卷积、完整状态布局、精度档和设备草稿链上限继续归模型。CPU／Metal 的具体算子或捕获能力尚未验证，应如实拒绝或使用已有实现；不能为了名义全平台支持消除 CUDA 专用快路。
- 当前公共端点是一主端点加可选 CPU 辅助，尚无多模型显存接纳或多 GPU 调度。本轮冻结这个实际范围；后续部署层可组合多个独立实例，不预建其资源调度器。
- HTTP 不保留跨请求 KV、前缀缓存未接线、Chat／Anthropic 未实现、加载后生成并持久化词表，均是已知功能范围，不能在四项关闭后再自动变成新阻塞项。
- 文本 codec 目前只核对 token ID 范围，不能证明同词表大小的两个 tokenizer 身份一致；匹配 tokenizer／模板仍是显式装配方的前提。自动来源绑定是后续制品功能，本轮不得把范围检查宣传成身份验证，也不因此扩成通用 loader／tokenizer 项目。
- 源码扫描发现的 `prepared_roles.h ↔ prepared_gguf_roles.h` 是模型内由 pragma once 保护的格式扩展 include。三处公共层测试 include 均受测试宏控制。这些不等于跨模块的运行时依赖环，不因计数就要求重构。

### 修复顺序与固定验收

1. **合同包：R4。** 先确定来源／执行方案／采样程序／请求状态的身份与生命周期，接入现有请求合同和拒绝路径；不开发新模型或新增 kernel。
2. **装配包：R1＋R2＋R3。** 将相互耦合的入口、冷计划和诊断一次收拢，避免每搬一个 helper 就重新编译大入口。公共执行调用原模型步骤，保持已有专用程序和资源权威。
3. **冻结包：** 对四项逐条给出提交与验收结果，检查下列理论场景及实际回归，然后标记本范围的职责／合同冻结。

- 宿主请求、选路、方案选择、取消／背压、错误分类与退休合同，以及现有源码边界检查。

- 只构建本包受影响目标，复用已有依赖和构建；不清缓存、不遍历构建所有目标、不下载模型、不为了冻结再开 kernel 优化或显存调研。
