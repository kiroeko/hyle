# 通用推理引擎设计方向

本文描述目标架构和迁移要求，不代表这些接口、产品入口或其它模型／平台已经实现。
原有 Qwen CLI 仍由 Qwen 驱动装配模型、请求与选项；文本 CLI 和 Responses 的 token 工作进程已使用公共请求入口。Graph、Compute 和 `engine/inference/` 已有可复用的执行与资源机制，迁移应保留它们。

## 参考与选择

参考本地 llama.cpp `23b0202a1`：`tools/cli/cli-context.cpp` 的 CLI 可以连接已有服务，
也可以启动本地服务，再通过 HTTP 提交请求；`tools/server/server.cpp` 注册 `/v1/responses`，
`server-context.cpp` 将协议请求转换为内部任务，服务端管理请求队列、模型上下文与结果。
Hyle 借鉴统一请求语义和协议适配边界，不预先要求本地 CLI 必须经过 HTTP 或复制其调度器。

## 目标结构

```text
 CLI ───────────────┐
                    ├─ 输入适配 → 请求／输出合同 → 引擎运行时
 HTTP Responses ────┘                             │
                                      模型适配 + 后端能力 + 冷期计划
                                                 │
                                     现有 Graph／Compute／资源与退休
```

- **入口**：CLI 负责交互和本地参数；服务负责 HTTP、协议、连接和错误格式。两者使用相同的引擎请求语义；本地 CLI 可直接调用引擎，远端访问则经 HTTP。
- **文本和制品**：模型制品识别、读取、tokenizer、对话模板及增量解码归引擎装配层。tokenizer 必须匹配制品；模型数学不依赖 HTTP 或 JSON。离线生成的草稿子词表等可作为显式输入，运行时的自动生成与持久化另按真实实现验收。
- **引擎运行时**：接收请求，管理会话、停止策略、接纳、输出背压、取消和结果交付；复用现有请求循环与缓存机制。传输断开不等于设备工作已退休。
- **模型适配**：按制品选择模型实现，模型负责自己的权重语义、数学、完整状态和可用程序；公共合同不暴露 Qwen 的 GDN、Phase 或 MTP 特定布局。当前首先接入 Qwen3.5-2B，不声称其它模型可运行。
- **后端**：能力由具体后端和模型共同报告，冷准备选择路径；Graph／Compute 保持模型无关。编译期平台差异和冷期分派优先，不能在每个 kernel 上增加不必要的抽象或同步。

Qwen 的缓存和权重报告适配器放在其模型目录，公共报告层只处理通用观测。源码直接 include 的依赖方向由 `inference_architecture_boundaries_test.py` 检查；该检查不覆盖全部间接或链接依赖，冻结审查仍需检查构建目标。

这是职责方向，不要求立即引入公共 ABI、插件系统、动态加载框架、第二个执行器或资源账本。模型和平台是否能扩展，要以具体接口和调用链审查；未运行的组合只能标为理论设计。

### 扩展边界审查

以下是按现有接口作的理论审查，不代表这些组合已实现或运行：

| 场景 | 现有边界与需要补充的工作 |
| --- | --- |
| 不含 GDN 的 dense GQA 模型 | 新模型可实现 `ModelProvider`／`ModelExecutor`，自行装载权重、准备图并拥有自己的 KV 状态；公共请求和输出合同不要求 Qwen 的 GDN、卷积或 MTP 状态。需在 `model_catalog.h` 和构建装配中登记提供者，并实际实现和验证模型；当前没有第二个完整消费者。 |
| MLA、滑动窗口或不同草稿结构 | 当前 `GenerationBatch` 是文本 token 请求，并不规定注意力状态布局；模型适配器可选择自己的状态与执行计划。Qwen 的单 NextN 层检查属于其模型实现，不是公共约束。新的缓存淘汰语义、草稿制品或非文本输入仍须扩展相应合同，不能声称当前已支持。 |
| CPU／Apple Metal | `Backend` 在编译期组合对应端点，模型在冷期选择；实际操作、状态复制和退休仍须由对应后端支持。Qwen 的自动 MTP、有界 CUDA 快路及设备接力目前按 CUDA 选择，编码行复制能力也只对 CUDA 声明；这不是 CPU／Metal 的功能承诺。批量结果回读当前使用 CPU／CUDA 的共同 Compute Context 与可保留 staging 资源；资格不支持或冷期资源不足时回落到独立读取，原生错误不会被当作回落。其它后端若实现这条快路，需要接入对应资源与退休合同；普通推理能否完成仍取决于图中所有操作和资源合同，尚未在本目标中验证。 |
| 增加一种后端 | 现有端点是编译期枚举和静态组合；新后端需要修改 `Backend` 的类型、构造和资源绑定，不能仅注册一个插件。准备阶段选择路径，不要求在每个算子上动态分派；新增端点必须补齐实际能力查询、失败、完成观察和退休验证。 |

这一分工与本地 llama.cpp `23b0202a1` 将模型记忆与单次批次上下文分开、TensorRT-LLM `46d9966b54` 区分运行准备及资源释放的边界一致；具体接口不照搬。请求合同目前仅承载文本 token；内部请求可选择已准备的采样配置，文本工作进程仍只准备一套，跨 HTTP 请求保留会话尚未实现。冻结时应保留这些限制，不能用接口名称代替第二模型或其他平台的验证。

当前已有内部请求执行合同及入口。Qwen 适配器可以借用已创建的模型，也可以装载并持有模型；两条路径通过同一输出消费者交付 token，不持有第二份 KV 或执行器。工作进程可在模型运行时将等待请求接入已释放的槽位；槽位不足时继续排队。正式程序提供内部标准输入／输出 token 工作进程，文本 CLI 与 Responses 文本服务通过它提交请求，并以逐请求确认控制输出背压。实际支持的协议字段和限制见[文本接口指南](../user/text-api.md)。本机 BF16、Q8、Q4 的八轮 512 token 对照中，每个格式与模式分别在同窗交错运行三进程：当前工作进程与当前原入口的普通／自动 MTP 输出逐项一致，完整进程吞吐范围重叠；另以抽取前 `af4148d39` 的入口和 Qwen 驱动各重编一个对象并复用当前底层库，同窗比较旧版 A/A、当前入口及上游；六格 512 个输出 ID 一致，当前完整进程范围每格都与至少一份旧版范围重叠。该重建不是独立旧版完整构建，也不覆盖其他负载。

内部 token 工作进程支持预先提交有限多轮，也支持打开输入后动态追加轮次并显式关闭；后续轮由原请求循环在上一轮发布后接纳，复用其会话与 KV。多轮接口按序交付 token 和从零开始的轮次完成事件，每个事件均须确认；单轮接口保持原有输出合同。后续轮按实际已提交的上下文检查容量；若放不下，仅该请求在真实退休后返回错误，提前停止释放的空间仍可用于下一轮。轮次完成不表示设备资源已经退休。新请求只有在原请求资源实际退休、输出终止事件被读取并释放后才能复用槽位；处于打开状态的其他会话不会独占全部空槽。内部 Qwen 执行器可让多个已准备采样方案共存；文本工作进程仍只配置一套，HTTP 接口尚不提供跨请求持久会话。

常驻执行按预设容量准备 prefill，已知日程可以按实际长度准备；动态接纳也可能改变合批形状。不同计划的浮点输出可能不同，随机采样即使 RNG 游标相同也不保证逐 token 一致；量化贪心输出也可能随批形状变化。评估这类差异应使用相同前缀、上游同格式模型和 BF16 teacher，并单独检查 RNG、状态发布及资源退休，不能只比较不同的生成文本。

本机 CUDA、Qwen3.5-2B 的短提示数值检查中，此前普通路径与当前量化子集 K1 的各 8192 个同前缀位置均通过各自的既有相对 KL／top1 护栏；K1 的 8064 个位置使用实际验证器首行，teacher 基线沿用旧记录。覆盖八个背景重叠提示、256 个位置的 4K 检查也通过合计护栏，但单个 4K 提示的 32 个位置未通过该 top1 门槛；这些样本不代表所有输入。Q8／Q4 的 prefill logits 会随 GGML CUDA 融合或分块变化，关闭融合尚未证明能总体改善质量。层零探针会发布额外中间结果并可能改变融合：在一个 Q8 512-token 输入上，启用探针改变了融合路径的输出，因此探针的中间结果不能直接代指未插桩图。抽取前入口与当前入口在六个相关固定输入及融合设置中输出一致，但旧入口复用当前底层库，并非独立旧版构建。长前缀、其他批形状及具体融合差异仍有限制，不能把这些结果写成所有路径的数值等价或冻结完成。相关测试和数字保留在提交记录及本地日志，性能对照见[性能表](../developer/performance/decode.md)。

工作进程使用 `engine/inference/model_provider.h` 的公共装载配置和提供者合同，`engine/model_catalog.h` 在程序装配时静态组合提供者。每个提供者只读检查自己的输入格式，匹配后由其完整验证和装载；无匹配或多个匹配会报错。当前只接入 Qwen 提供者，原有 Qwen CLI 仍单独转交其驱动。该机制没有动态插件或第二个模型执行器，也不证明其他模型已支持。Qwen 装载器在冷期复用已有 MTP、设备验证和接力策略；多会话自动 MTP 当前关闭。显式 K1／K3 已用本机 Q4 和真实 tokenizer 验证两个并发 Responses 流，断开其中一个后另一个及后续请求完成；日志观察到两请求共同进入验证批次。单卡双请求、每臂三进程的短提示筛查中，现有子集头在中英混合组有收益，在另一组多语言提示上 Q8／Q4 K1 和 BF16 K3 均慢于普通生成；同组 Q8／Q4 全头 K1 则快于普通生成。该结果不能推出所有模型或设备的默认策略。另用旧日程的 8 个短提示自然生成，比较真实双请求验证器：相对上游 BF16 同前缀，K1 首行的 Hyle／上游单请求 Q4 top1 一致数为 129／146、127／146，平均 KL 为 0.07024／0.06996。K3 的 220 个位置包含 94 个首行和 126 个后续行，Hyle／上游 Q4 top1 均为 197／220，平均 KL 为 0.06650／0.06600；只统计实际提出 3 个草稿且验证 4 行的成员，后续行还要求先前草稿实际被接受、其预测与已发布 token 一致。诊断使用 commands 重放；这些经过筛选的小样本不代表多会话 MTP 的完整性能或数值质量已经验收。

文本层的 `engine/text/runtime.py` 负责消息编码、请求提交和有序文本交付；CLI 与 Responses 都使用这条路径。`contracts.py` 描述 token 传输合同，`worker_client.py` 连接内部工作进程；`server.py` 负责 HTTP 路由、连接和流式传输，`responses.py` 负责 Responses 字段与事件格式，`app.py` 在启动时组合入口和路由。输出消费者接收文本之后才归还 token 配额；传输失败由原请求的取消与退休路径处理。

## 请求与生命周期

模型装载和设备选择完成后形成可复用的运行上下文。每个请求拥有独立身份、输入、生成配置、停止条件和输出消费者；会话及模型状态的所有权应明确，不能通过协议对象直接修改设备事务。

当前内部装载合同将来源资产、执行准备和采样程序配置分开。公共资产合同提供主来源和具名附加资产，由模型提供者解释角色和验证来源；Qwen 识别草稿词表与草稿头，未知角色报错。请求日程可携带初始随机种子；未指定时沿用模型默认值，接纳时生成游标，之后的随机位置属于会话已提交状态。工作进程的 `--seed` 是发给请求的默认值；Responses 尚不接收逐请求种子或采样参数。Qwen 内部装载合同可预设多套采样方案，请求按索引选择；只有执行器声明可共存时，公共调度器才在同一执行期间接纳不同采样方案。各实际计算波仍按模型已有兼容条件分组。

引擎应能提交请求、交付有序增量输出、观察完成或失败、请求取消，并在消费者不能继续接收时施加背压。取消只停止后续可停止的工作；已提交设备工作的完成观察和真实资源退休仍走原 Graph／Compute 路径。模型请求槽位退休和下游输出槽位释放分别判断：正常消费须读到终止事件并释放；请求句柄被放弃时丢弃未读输出、请求取消，仍须等原模型确认退休才能复用槽位。文本增量解码需处理跨 token 的 UTF-8 边界；传输写入成功与模型状态提交是不同事件。随机数、状态版本、MTP 接受及输出顺序沿用现有正确性合同。

公共请求驱动负责依序服务输出、推进请求、观察退休和接纳输入；Qwen 适配器仍拥有模型状态、图执行以及具体输入准备。驱动通过编译期绑定调用适配阶段，不创建第二个执行器或设备资源所有者。其余 Qwen 生成装配仍需继续审查，不能因抽出这个循环就认为模型接入问题已全部解决。

能力和参数在装载、准备或请求接纳时校验并尽可能选路；不能提前确定的资源权限、Source 和完成状态仍在执行时检查。默认策略、正确性限制、性能选择分别表达，并能解释拒绝或回落原因；不以某次单模型测试结果伪装共同正确性条件。

当前有界请求的轮数、token 范围和输入／输出预算由公共接纳检查统一表达；Qwen 使用该检查，并在后续轮按实际已提交上下文检查新输入、上一轮 pending 和输出额度。这是已选择的有界政策，不强迫滑动窗口或其他模型采用相同容量规则。

### 混合请求的设计检验

以同一模型的三个并发请求为例：A 选择子词表草稿头和 K3，B 选择全词表头和 K1，C 使用普通随机采样。目标是共享同一份目标权重；每个请求独立拥有其输出配额、停止政策、会话状态和 RNG 游标。草稿资产与执行程序在冷期准备并保持不可变；请求引用它们，设备工作真正退休前不得替换映射或回收资源。草稿与验证方法由模型实现，不要求其他模型复制 Qwen 的 K 上限、状态布局或修复步骤。

调度应根据已准备程序的实际兼容性组成执行批；不能混合的请求分别运行，并避免不兼容请求永久阻塞其他请求。可混合的草稿深度、采样和词表由模型及后端能力决定，不预设所有字段必须相同。驻留会话数、单批序列数、在途深度及物理执行槽分别计量；准备多种方案时预算必须覆盖能同时存活的资产、状态和工作区。目标权重、激活、KV 与草稿头的编码和计算精度分别描述，不以一个“模型量化格式”代替。

共享前缀是可复制写入的不可变计算状态，必须包含续算所需的 KV、卷积和递归状态；完整会话检查点还包含 pending、草稿及 RNG。底层前缀目录按模型、数学身份和由可信调用方指定的共享域共同匹配；内部请求将该域传给 Qwen 的查找和发布。默认域 0 保留本地原有共享行为，并不自动隔离用户。服务若要启用前缀缓存，必须由可信服务层分配共享域，不能相信未经验证的客户端域值。Qwen 的 Q4 和 BF16 真实 prefill 状态已检查同域命中与跨域不命中，宿主测试覆盖 pin 与淘汰；公共工作进程尚未接线，不能据此声称服务具备租户隔离。本地 vLLM `276fbcff27` 在块哈希的额外键中包含适配器、多模态和可选 cache salt，可作为共享域设计参考。

现状仍不能执行上述三请求混合：Qwen 的缓存计划绑定普通或 MTP，装载时只选择一套草稿资产；公共工作进程未启用前缀缓存，HTTP 也不保留跨请求 KV。在同一推理模式下，Qwen 内部接口已用 BF16、Q8 和 Q4 短提示分别检查普通、K1、K3 的三套采样方案，包括初始混合批、动态接纳、独立 RNG 与拒绝非法配置。配置子词表时，未修改的贪心方案使用子词表，随机或带 logits 修改的方案使用完整草稿头；K1／K3 随机方案在三格式同前缀、同种子小样本中与未装载子词表的结果一致。BF16 另检查了已准备的 Q4 草稿头；默认随机或默认贪心均可与另一方案共存。显式子词表没有贪心消费者时仍会报错。

内部请求可以指定不超过已准备上限的每轮草稿数，同一 Qwen MTP 模型可接纳 K1 和 K3 请求，并按现有形状与采样兼容性组批；超出准备上限的请求在接纳时被拒绝。BF16、Q8、Q4 子词表小样本检查了混合 K、动态接纳和请求独立的 RNG。Q4 的八个提示产生 114 个真实双请求验证首行，K1 与 K3 各 57 个：两组分别与 BF16 teacher 在 51 个位置 top-1 一致，均与同格式 llama.cpp 的一致数相同，并通过既有相对 KL 护栏。这些短提示不能代表所有形状。零草稿上限只表示不提出草稿，仍使用 MTP 状态和程序，不等同普通生成。公共工作进程和 HTTP 尚未提供请求级草稿上限；贪心请求也不能在已装载子词表时独立选择完整头。

公共 `ModelExecutor` 最终仍调用 Qwen 的生成装配；第二个模型是否无需复制它，还没有实际消费者证明。多模型及多设备还需要独立的模型实例、预算与资源接纳合同，不能把单主端点加可选 CPU 辅助误写为多设备调度。

后端应在冷期提供真实算子、编码搬运、捕获、同步与退休能力，模型再结合自身数学约束选择程序；默认策略和测得的性能偏好与正确性限制分开。现有 CUDA 快路可以保留，其他后端当前只有理论审查。量化 tokenizer 子词表由固定提示及原 ID 顺序补齐，不能推断所有语言的接受率；加载后自动生成、来源绑定及持久化仍未实现。

## CLI 与 Responses

目标提供命令行入口和 HTTP 服务。协议边界需要能够容纳 OpenAI Responses、OpenAI Chat Completions 和 Anthropic Messages；先实现 Responses，其余两种在实现和验证前不声明支持。每个协议负责解析、字段校验、错误和流式事件转换，不把某一种协议的 JSON 对象作为模型或调度器接口。内部请求与事件须保留消息顺序、角色、内容、生成选项、使用量和完成原因，扩展内容类型时不能将其静默压成纯文本。

Responses 首版以文本请求和文本输出为目标，需明确并测试实际支持的字段、同步与流式行为、取消、错误以及使用量统计；尚不支持的字段或能力应明确拒绝。工具调用、多模态、服务端持久会话等按实际实现单独声明。流式协议的事件格式由适配层实现，参考 [OpenAI Responses 流式文档](https://developers.openai.com/api/docs/guides/streaming-responses)；模型线程只交付已提交输出，传输断连通过请求取消传播，实际设备退休仍由原执行链完成。

模板由模型制品及其配置选择，不能把 Qwen 的某个 Jinja 模板编码成通用消息合同。模板渲染、tokenizer 和增量文本解码属于文本适配层；缺失或无法执行的模板及不支持的消息内容应有明确结果。当前文本入口使用本地 Python tokenizer 和模板；`hyle::io::http` 提供 HTTP/1 帧处理，文本服务的监听、路由和连接生命周期由 Python 前端实现。服务默认端口为 2048，支持时默认启用指标；协议范围见[文本接口指南](../user/text-api.md)。

## 迁移与验收

1. 沿当前 Qwen 调用链梳理装载、请求、输出和模型状态所有者，定义可由 CLI 和服务共同消费的最小合同；逐步从 `qwen35::run` 提取装配，而非复制生成循环。
2. 用本地 Qwen3.5-2B 接入该合同，保留普通、采样与 MTP 已有路径；先证明输出、状态、取消和资源退休，再迁移入口。避免将 Qwen 私有状态当成通用模型接口。
3. 接入与制品匹配的文本编解码和模板；CLI 与 Responses 服务各自使用共同请求合同，覆盖非流式和流式输出、错误、断开及背压。先通过同一模型的端到端测试，再声明具体兼容范围。
4. 验证基础库独立构建及依赖方向；按仓库约定在同窗交错对比完整进程、prefill 和 decode，检查普通／MTP 及已支持采样，没有超出实测噪声的退化。只构建相关目标并复用现有目录。
5. 冻结前审查模型、后端、请求、状态和协议边界，以理论方式检查其它模型与 CPU／Metal 的接入；如实列出未验证部分。M2 前不下载其它模型，也不把理论可扩展性写成已支持。
