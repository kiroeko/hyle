# 推理引擎的两项核心期许

依据用户2026-10-30的明确要求。本页记录长期开发目标和取舍，供架构设计、实现、实验与完成判断共同使用；
当前任务与估计进度仍只在[推理进度](../developer/inference-progress.md)维护。

## 1. 面向各种模型的模块化底座，架构成本尽量留在冷期

HYLE要成为支持多种模型的推理引擎。目前能完整验证的本地2B Qwen路径是验证消费者，
不是共同形状、状态、执行阶段或模块边界的定义。后续底座成熟后再租用更强设备扩大验证，
当前先处理本机能实现、能检查的共同能力与原模型组件，不能用硬件限制固定架构。

持续参考SGLang、llama.cpp、vLLM、TensorRT-LLM、DeepInfer等成熟引擎，结合不同模型的真实需求做抽象。
记录实际参考版本、源码和适用条件；提炼职责与机制，而非照搬大型动态接口或某一模型的形状。
期许定义目标，不能替代技术方案的正确性依据。具体边界须同时结合实际模型需求、HYLE现有机制和主流引擎的成熟做法，
核对真实源码及适用条件，再以数值、寿命、变更影响和性能验证；不能只凭“符合期许”或引用引擎名字选方案。

共同部分应有明确的所属模块、依赖方向和接口，使修改一个机制时不必连带改写许多模型；
接入新模型主要增加其数学、权重含义和完整状态适配，减少重复实现同类请求、缓存、装配与执行政策。
模块化是否有效，要看实际依赖和接入工作量，不能用目录数量、公共类型数量或接通一个共同驱动代替。

| 需求变化 | 共同底座应表达的内容 | 模型保留的内容 |
|---|---|---|
| 稠密、MoE及不同投影／量化布局 | 冷装配、放置、端口与执行资源合同 | 权重角色、数学、codec／scale语义及合法融合 |
| KV、MLA、卷积及递归状态 | 实际存储域、完整版本、权限、缓存与寿命 | 状态布局、更新方程和合法恢复边界 |
| 普通生成及不同MTP结构 | 请求额度、批次推进、实际阶段结果、提交观察与退休 | 提案／验证／修复数学、RNG地址及完整状态发布顺序 |
| 多请求、多会话及部署拓扑 | 接纳、分组、背压、取消、资源与依赖事实 | 兼容条件、实际设备能力及模型工作形状 |

优先把模型分析、能力选择、形状族、资源布局、程序与端口准备、调度计划等工作放到推理前的计划和加载阶段。
热路径消费已经准备好的事实，采用静态直接调用、稳定缓冲与原资源机制；逐token的动态分派、查找、分配、
重复装配、搬运和同步都应有实际必要性及成本证据。状态、lease代际、请求身份和真实退休等动态正确性检查仍须保留。

架构设计以保持或提高推理速度为前提，不能以模块化收益抵销热路径退化；
通过冷期准备和实际测量消除新增抽象带来的运行成本。
共同机制继续复用Compute／Graph的原执行、资源和退休权威，保持基础库独立使用能力。
不为引擎增加另一套执行器或账簿，也不把不同模型强行改写成Qwen的阶段数、状态银行或单设备假设。

## 2. 性能是项目成立的必要条件，交付目标是默认就快

如果没有有竞争力的性能，用户没有理由从llama.cpp等成熟引擎转向HYLE。
纯GPU推理是主要场景，**decode速度是重中之重**；架构工作的价值也必须接受完整推理性能的检验。

**对每个受支持模型，都要尽量达到专门为该模型准备的引擎的执行效率，尽量不因架构降低性能。**
共同底座应能保留模型特有的合法融合、布局、状态更新和执行快路径，在冷期按模型与设备准备合适的程序及资源，
热期直接执行。不能为统一接口强迫模型承担不需要的阶段、通用形状、数据搬运、同步或重复计算。
这是一项持续检验的性能愿景，不是已经达到零开销的结论；具体方案仍须核实际模型需求、成熟引擎源码与适用条件，
并用该模型的完整消费者评估新增架构成本，不能将一个模型的收益推广为所有受支持模型的结论。

目标是用户按默认方式构建、按正常默认用法运行，就能获得优化收益。
调研期间可以有提案、诊断开关和显式候选；最终应收敛为冷期自动选择的适用快路径、必要的正确回落，
或撤回没有净收益的实现。保留设备、精度和内存预算等真实用户决策，不让用户靠挑选内部实现获得常规速度。

显式32K草稿词表等特定配置的领先可以证明一个方向有潜力，但不能作为通用默认配置性能完成的依据。
它改变了适用条件，必须另列；默认完整词表、普通／MTP和其它真实配置的差距仍须继续解决。

显存也重要：不能轻易用接近翻倍的占用换取速度；相对llama.cpp的小幅差异可以结合实际收益权衡，
不追求毫无差别的字节数。区分原权重、额外常驻资源、缓存与独立进程的物理采样峰，不能混用。

性能判断以当前完整消费者为准，记录默认配置下普通／MTP、单轮／多轮及相关批次的decode，
同时保留prefill、启动、综合速度和内存／显存。对照记录实际版本、输出与工作量差异及测量波动。
局部kernel收益、特定prompt或额外开关的成绩不能代替整引擎收益；数值、资源寿命和请求语义继续保持正确。

## 如何应用到日常开发

每一片架构工作都说明它处理了哪些不同模型需求、共同机制归谁、接入新模型还需要写什么，
以及哪些准备移到冷期、热路径还承担什么成本。用实际调用链和消费者检验，发现新的耦合继续调整。

每一片性能工作都区分默认路径和实验条件，说明收益是否已经进入默认构建与正常用法，
并用相关完整消费者核对速度、内存和正确性；成功机制收敛进原底座，失败候选记录边界后撤回。

整体架构完成需要跨模型需求、模块边界、接入成本和冷／热职责的证据；
共同步骤驱动或有限组件检查完成只证明其各自范围。尚未运行的大模型与部署能力继续如实标记。
