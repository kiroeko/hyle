# HYLE 的动机与设计取舍

HYLE 的产品目标是完整推理引擎，同时让基础模块能独立构建、安装和使用。
当前主要工作是底层推理支持：用真实模型检验计算、状态、缓存、资源寿命和调度的组合，
逐步形成可维护的引擎。完整服务、协议和应用 API 的开发次序见[推理工程计划](../implementation/inference-roadmap.md)。

## 为什么需要共同底座

高性能 C++ 程序可以分别选到成熟的 allocator、容器、SIMD、调度器、I/O 和计算库，
但仍要自行对齐它们的资源 owner、错误、线程、取消、完成和构建方式。
同一个 buffer 在两个库中都合法，并不表示它们共享设备、stream、布局、读写权限或释放时机。
局部 kernel 很快，也可能被整条调用链中的重复分配、转换、拷贝和同步抵消。

HYLE 的集成价值在于让这些机制可组合：共享可解释的资源与执行合同，保留原生实现的优势，
让上层可以选择需要的模块。成熟库已经能自然解决的问题优先复用；只有额外组合能减少成本、
填补实际能力缺口或改善调用方式时，包装和自实现才有价值。

## 为什么用真实推理检验设计

孤立微基准很难暴露完整旅程的问题。它可能省去模型加载、权重上传、布局准备、结果发布，
也可能在每次测量前重新注入正确状态，从而漏掉连续推理的数值漂移和资源积压。
项目过去还遇到过计时范围不一致、代码放置影响极短循环，以及为了 benchmark 暴露不自然接口的问题。

真实模型会同时要求：

- 权重加载、映射与有界传输，压缩格式和实际计算精度的接线；
- prefill、decode、MTP 与不同输入长度下的计算和状态继续；
- 多会话的共享、分叉、淘汰、恢复，以及多请求的接纳、取消和背压；
- CPU、GPU 和混合路线各自正确的执行、完成、资源预算与关闭。

这些要求让接口问题有具体反例，也让优化能落实到加载时间、prefill/decode tokens/s、
会话总耗时和内存／显存变化。局部优化只有进入完整消费者后，才能说明它是否改善推理。
测量方法见[性能说明](../developer/performance/README.md)，已有结果见[模块数据](../developer/performance/modules.md)
和[推理性能资料](../developer/performance/decode.md)。

## 领域语义留在合适的层

模型文件、权重角色、tokenizer、生成和接受策略、会话与请求编排属于 `engine/`。
Compute／Graph 提供模型无关的数学、状态、资源和执行机制，不按模型名单建立第二套执行器、
线程池或退休系统。模型实现可以组合已有能力，不能要求基础模块了解某个模型的 token 或层名。

这不是要求所有硬件都表现成同一种 runtime。CUDA 的队列和 capture、Metal 的资源与命令、
Vulkan 的显式依赖、CPU 的工作线程具有不同成本和能力；共同接口表达相同的数学与所有权，
原生实现保留真实差异。统一地址不自动代表零复制，采样完成也不自动证明所有资源已经退休。

资源流送、批处理数值管线和异步服务还能检验基础机制是否过度依赖推理：同一份 lease、
有界 staging 或取消／drain 机制，应当在去掉模型语义后仍然自然。
这些用途帮助检验抽象，不是要求项目同时建设渲染器、数值应用或通用 Web 框架。
具体边界见[产品范围](hyle-scope.md)、[基础设计](foundation-design.md)和[推理架构](inference-design.md)。

## 怎样判断做得是否正确

用户应能按公开产品选择、构建和调用能力，而不必排列算子 Provider、填写内部宏或了解第三方装配细节。
维护者应能沿有限职责定位修改：新模型主要组合数学与状态，新实现落在对应 Provider，
资源和失败合同由原所属模块承担。无法自然组合时，应修复边界，而不是让每个消费者重复接线。

性能结论限定于实际模型、格式、输入、设备、版本和完成边界。
正确性、取消、部分失败、并发和关闭也是功能的一部分；成功执行一例不能代替这些路径。
独立使用基础库与使用完整引擎都应成立，源码、静态库和共享库交付也应有自然使用方式。

主要风险是脱离实际调用扩大范围、为微小计时差异破坏接口、过早建立万能抽象，
以及保存大量旧结论却不再说明适用条件。设计文档保留有用的理由和反例，
API 用法在用户文档维护，性能事实按日期与执行身份记录。
